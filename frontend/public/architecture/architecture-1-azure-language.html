Objectives

  • Establish a first-party, fully managed reference pipeline
  • Keep PII handling inside Azure AI Language, with no model prompt to govern
  • Produce the same versioned output contract as every other architecture
  • Make cost and latency directly comparable to the LLM-based options

Users & stakeholders

  • Solution architects choosing between managed services and a hosted LLM
  • Compliance reviewers who need a named, certified PII service
  • Engineers running the benchmark from the browser UI
  • Finance owners applying 90% Speech / 70% Language discounts

Value & measured outcome

  • Highest per-call price of the three: $0.031069 discounted
  • Highest word error rate of the three: 5.36%
  • Weakest on the CUSTOMER channel: 7.42% WER vs 3.69% for REP
  • Strongest governance story: no prompt engineering in the PII path
Decision framing. Architecture 1 is roughly 2.1× the cost per call of Architecture 2 and has ~60% more word errors, but it is the only implemented option whose redaction decision is made by a dedicated Azure AI Language PII model rather than a general-purpose LLM under a prompt.

No regex in this architecture. Deterministic pattern matching exists only in the DeepSeek architectures, where it supplies candidate hints to the model. In Architecture 1 the PII decision is made entirely by Azure AI Language; the only local text manipulation is applying the returned spans and scrubbing those literal values out of the generated summary.

Latency contract. Every successful result carries a latency block with stt_seconds (time to a full transcript), downstream_seconds (the whole post-transcript window, measured once around the concurrent endpoints and the two local redaction stages), and end_to_end_seconds. A failed architecture reports latency: null instead. The frontend renders these as an end-to-end latency table plus a per-stage latency breakdown.

Entity matching and redaction rules

  • Every returned entity is re-verified: the span in the source turn must equal the returned text, or the run fails loudly
  • Spans are applied back-to-front per turn; overlapping spans are dropped in favour of the earliest, longest one
  • Replacement text is derived from the category: [PERSON], [PHONE_NUMBER], [US_SOCIAL_SECURITY_NUMBER]
  • Turn ids, participants, and timings survive redaction unchanged; derived fields (lexical, ITN, word timings) are dropped
  • The transcript_redaction and summary_sanitization stages are timed separately, so local redaction cost is visible next to the endpoint cost
  • The summary is then scrubbed of every detected literal value, case-insensitively, longest value first

Why the unredacted transcript is sent twice

  • Conversation PII must see raw values to detect them at all
  • Summarization quality degrades if it only sees placeholders, so it also receives the original text — this matches the client-confirmed production flow
  • Both requests are built up front and dispatched together, so sending it twice costs bandwidth, not latency
  • Safety therefore comes from the post-hoc redaction pair, not from input filtering
  • Summarization additionally requires Azure's Agent/Customer roles; benchmark labels are projected for that request only
  • Source turns and the PII request keep their original participant labels

5. Features and non-functional requirements

Functional

  • Dual-channel transcription with channel identity as authoritative speaker identity — no diarization is billed
  • Word-level timestamps and lexical / ITN / masked-ITN forms from the Speech SDK
  • Full-category PII detection with confidence scores per entity
  • Issue and resolution summary aspects
  • Typed placeholder redaction of both the conversation and the summary
  • Optional WER scoring and optional PII precision / recall / F1 scoring

Non-functional

  • Asynchronous by construction — real-time STT runs at 1×, so every user-facing run is submitted, polled, and read back
  • Early handoff — downstream work is submitted as soon as this architecture's own STT result lands, not after all three engines finish
  • Isolation — a failed architecture is reported independently with its error string and a null latency block
  • Determinism downstream — redaction is span application, not model output rewriting
  • Integrity — entity spans, turn counts, and ground-truth digests are all validated
  • No secrets in the repository — Entra ID only, key auth disabled on the resource
  • Reproducibility — the checked-in mock call is the default input for CLI, container, and UI alike

Accuracy and cost telemetry

  • WER, accuracy, substitutions, deletions, insertions, hits — overall and per participant
  • Finalization lag distribution: mean, median, p95, max
  • Character counts feeding the Azure Language text-record model (1,000 characters per started record)
  • Applied discounts: 90% Speech, 70% Azure Language
  • Volume tiering applied when projecting to 100,000 calls

Measured position in the benchmark

  • Accuracy: 3rd of 3 — 5.36% WER (MAI real-time 3.34%, MAI batch 4.15%)
  • Latency to transcript: tied 1st — 504.3s on a 504.2s call, reported as latency.stt_seconds
  • Downstream: two overlapping Azure AI Language jobs plus two sub-millisecond local stages
  • Cost: 3rd of 3 — $0.031069 vs $0.014834 and $0.014913
  • Governance: 1st — no prompt, no model temperature, no JSON schema to validate

6. Deployment and runtime notes

Local runtime

  • docker compose up --build starts the backend on port 8000 with a health check
  • cd frontend && bun install && bun run dev starts the UI on port 3000
  • The host ~/.azure profile is mounted read-write so DefaultAzureCredential can refresh tokens mid-run
  • Uploads and results are bind-mounted so they survive container restarts
  • uv run python data/stt.py still benchmarks the checked-in mock call from the CLI

Configuration

  • AZURE_LANGUAGE_ENDPOINT must be the Cognitive Services data-plane endpoint, not a Foundry project URL — the adapter rejects the latter at construction time
  • AZURE_LANGUAGE_API_VERSION defaults to 2024-11-01
  • AZURE_REQUEST_TIMEOUT_SECONDS defaults to 300
  • ALLOWED_ORIGINS pins CORS to the local frontend
  • Local development loads an ignored repository-root .env; deployed environments inject the same names

Identity and network

  • Key-based auth is disabled on the Speech resource, so managed identity is the only path
  • In Azure Container Apps, enable a managed identity and grant it Cognitive Services Speech User on the Speech resource
  • With a user-assigned identity, also set AZURE_CLIENT_ID on the container
  • Keep egress open to *.cognitiveservices.azure.com
  • Architecture 1 needs no outbound WebSocket — only HTTPS to Speech and Language

Known runtime caveats

  • Speech tokens are fetched once per run and never refreshed; calls longer than the Entra token lifetime will fail mid-stream
  • The Conversation PII poll loop is bounded — it raises a timeout rather than hanging
  • Concurrent benchmark jobs are capped at 2 by default
  • The job registry is in-memory; a backend restart loses in-flight jobs, though completed reports remain on disk
Infrastructure scope. The checked-in Bicep provisions only the Foundry resource and DeepSeek deployment used by Architectures 2 and 3. The Speech and Language resources this architecture consumes are referenced by endpoint configuration, not created by this repository.
