Architecture 3 — MAI batch + DeepSeek

The same MAI transcription model and the same single DeepSeek redaction and summarization call as Architecture 2, but transcription happens after the caller hangs up, as a concurrent fan-out of voice-activity-delimited utterance requests.

1. Business context

Architecture 3 exists to isolate one variable. It shares the transcription model, the prompt, the redaction code, and the output contract with Architecture 2, so the only difference measured is real-time streaming versus post-call batch. Keeping it separate makes the latency and cost trade explicit instead of buried in an option flag.

Objectives

  • Quantify what post-call processing costs in wall-clock time, holding quality constant
  • Preserve real speaker turn timing without a live streaming session
  • Keep an identical downstream contract so the comparison stays honest
  • Give a fallback path for environments where outbound WebSocket is not available

Users & stakeholders

  • Teams that only have recordings, not live call audio
  • Platform owners in locked-down networks where real-time streaming is blocked
  • Architects deciding whether a ~18 second post-call delay is acceptable
  • Finance owners comparing near-identical token bills

Value & measured outcome

  • Costs only $0.000079 more per call than Architecture 2, purely because the DeepSeek response is slightly larger
  • Accuracy sits between the other two: 4.15% WER
  • Best single-channel result in the whole benchmark: 2.03% WER on the REP channel
  • Weaker on the CUSTOMER channel at 6.97%, which widens the spread
  • Costs 17.75 seconds of post-call latency the real-time path does not pay
Why utterance fan-out rather than one whole-file request. The whole-file enhanced response exposes a single full-duration phrase per channel, which cannot be turned into chronologically interleaved speaker turns. Submitting the already-detected voice-activity utterances concurrently keeps real offsets and real turn boundaries. The price is request fan-out: turnaround rose from the old 7.8 second whole-file result to 17.75 seconds.

3. Processing pipeline and latency boundaries

The defining difference: nothing at all happens while the call is in progress. The entire pipeline is serialized after the recording is complete, so the transcript is ready at call duration plus turnaround rather than at call duration. Five stages are measured — batch transcription, a local regex scan, one Foundry call, and two local redaction stages.

Latency contract. Every successful result carries a latency block with stt_seconds (time to a full transcript, which here includes the post-call turnaround), downstream_seconds (measured once around the regex scan, the model call, and the two local redaction stages), and end_to_end_seconds. A failed architecture reports latency: null. Downstream work is submitted the moment this architecture's own STT result is finalized, so it never waits for the other two engines. The frontend renders the end-to-end table plus a per-stage breakdown.
Adapter detail. Architecture 3 delegates the entire downstream stage to the same processor object Architecture 2 uses, then overwrites only the stt stage of the result with its own batch metrics. That is why the two architectures cannot drift apart in redaction behaviour — there is one implementation, not two.

4. Batch transcription mechanics

Request shaping

  • Each channel is submitted as mono because the model does not separate stereo channels
  • The local voice-activity detector cuts the channel into utterances: 20 ms frames, RMS gate, half-second silence closes a segment, 20 second hard cap
  • Each utterance becomes an in-memory WAV clip posted as multipart form data
  • Requests are issued through a bounded worker pool per channel, both channels in parallel

Resilience

  • Throttling and server errors are retried up to three times per clip
  • Retry-After is honoured when present, otherwise exponential backoff
  • Client errors are returned immediately rather than retried blindly
  • Upload file handles are rewound before each retry
  • Empty clip results are dropped rather than emitted as blank turns

Turn fidelity

  • Each clip's text is stamped with the real offset and duration of the utterance it came from
  • Turns from both channels are merged chronologically; overlapping speech stays as two overlapping turns
  • A fallback estimates timings only if a response has no usable phrases or breaks the 1,000-character conversation-item limit; the benchmark run reports this flag as false
  • Word-level timings are not available from this engine

6. Features and non-functional requirements

Functional

  • Post-call transcription of complete recordings with no live session
  • Real speaker turn timing preserved through utterance-level requests
  • Single-call PII redaction plus issue-focused summarization
  • Typed placeholder redaction of conversation and summary
  • Optional WER scoring and optional PII precision / recall / F1 scoring
  • Full token accounting including retried attempts

Non-functional

  • Asynchronous — a run still takes about as long as the recording, so it is submitted and polled
  • Early handoff — downstream work is submitted as soon as this architecture's own STT result lands, not after all three engines
  • Throttle-aware — fan-out is bounded and retries respect server backoff
  • Network-friendly — HTTPS only, no outbound WebSocket requirement
  • Deterministic downstream — temperature 0, schema-strict, spans re-derived from source
  • No secrets — Entra ID token per run
  • Comparable by construction — identical downstream code and contract to Architecture 2

Measured position in the benchmark

  • Accuracy: 2nd of 3 overall at 4.15% WER, but 1st on the REP channel at 2.03%
  • Latency: 3rd of 3 — latency.stt_seconds of 521.9s versus ~504.4s for both real-time paths
  • Downstream: one model call plus three local stages, summed into latency.downstream_seconds
  • Cost: 2nd of 3 at $0.014913, essentially tied with Architecture 2
  • Fan-out cost: turnaround rose from 7.8s whole-file to 17.75s per-utterance

Cost model inputs

  • Audio hours multiplied by channel count: 0.280093 submitted hours for the benchmark call
  • Utterance fan-out does not change the billed audio duration, only the request count
  • MAI transcription priced per submitted audio hour with the 90% Speech discount
  • DeepSeek input and output tokens priced separately with no discount
  • Totals exclude hosting, storage, logging, and egress

7. Deployment and runtime notes

Local runtime

  • docker compose up --build starts the backend on port 8000
  • cd frontend && bun install && bun run dev starts the UI on port 3000
  • The host ~/.azure profile is mounted so the container can authenticate
  • Clip WAVs are written to a scratch directory per request and cleaned up immediately
  • uv run python data/stt.py runs all three STT engines from the CLI

Configuration

  • Shares AZURE_FOUNDRY_ENDPOINT, AZURE_FOUNDRY_DEPLOYMENT, and SYSTEM_PROMPT_PATH with Architecture 2
  • Speech fast transcription uses a pinned API version in the benchmark module
  • Per-clip request timeout is generous by design; the fan-out is the bottleneck, not any single clip
  • AZURE_FOUNDRY_MAX_ATTEMPTS defaults to 2

Identity and network

  • Key auth is disabled on the Speech resource, so managed identity is the only path
  • Cognitive Services Speech User covers the fast transcription data actions
  • Egress to *.cognitiveservices.azure.com and *.services.ai.azure.com over HTTPS is sufficient
  • This is the architecture most likely to survive a locked-down VNet, because it needs no real-time socket

Known runtime caveats

  • Request fan-out scales with utterance count, so very long or very fragmented calls increase turnaround and throttling pressure
  • One Entra token per run, taken at the start
  • The job registry is in-memory; completed reports survive on disk, in-flight jobs do not survive a restart
  • Concurrent benchmark jobs are capped at 2 by default

8. Current implementation vs the complete intended pipeline

AspectImplemented todayIntended / complete pipeline
Post-call boundary The benchmark has the whole file up front, so it explicitly waits out the call duration before starting, and reports time to full transcript as call length plus turnaround. In production the wait is real: the recording simply does not exist until the caller hangs up. The reported number already reflects that.
Whole-file transcription Not used for turn output, because the enhanced whole-file response collapses each channel into one full-duration phrase. Per-utterance fan-out remains necessary for interleaved speaker turns until the batch response exposes usable phrase-level boundaries.
Redaction and summarization One shared DeepSeek call reported as a single llm_api_call stage, identical to Architecture 2 — the adapter only replaces the stt stage of the result, so the four downstream stages and the downstream latency are produced by the same code. Unchanged by design; divergence here would invalidate the comparison.
Cached default comparison The checked-in results file holds STT metrics and pricing usage only, so the UI reports PII accuracy as not scored for that historical run. A live annotated run produces the architecture block plus precision, recall, F1, category accuracy, alignment rate, and leakage rate.
Architecture 4 Not implemented and not part of the three-way benchmark. A future Azure Communication Services option combining call audio, STT, and PII handling.
